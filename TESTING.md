# Testing

Two halves that share one number.

**Coverage** is measured with the Go toolchain and held to a per-package
contract by `covcheck`. **End-to-end** tests are NixOS VMs, one per scenario,
each booting a machine with real block devices standing in for cartridges.

They are not separate pipelines. The instrumented binary the VMs run emits the
same raw counter format `go test -cover` emits, so one `go tool covdata`
invocation unions them into a single profile. Coverage from driving the real
CLI inside a VM lands in the same report as coverage from a unit test.

```
go test -cover ──┐
                 ├─→ raw covdata counters ─→ merged.profile ─→ report / gate / lcov / html
kura -cover in ──┘
   a NixOS VM
```

## The inner loop

```sh
make cover        # unit coverage, merged, reported per package
make cover-todo   # the biggest uncovered blocks, worst first
make cover-html   # browsable report
make test         # just the tests
```

`make cover-todo` is the one that moves the number. A percentage says how far
there is to go; that says what to write next, sorted so the cheapest wins are
at the top.

## The full loop

```sh
make e2e          # every VM scenario
make e2e-1 S=bitrot
make cover-all    # unit + every scenario, merged and gated
make check        # nix flake check: units, gofmt, vet, covcheck, every scenario
```

`make cover-all` builds `.#coverage`, which depends on every scenario — so it
runs the whole VM suite and then gates the result. It writes
`merged.profile`, `coverage.html`, `coverage.lcov`, `report.md` and
`uncovered.txt`.

## Coverage

### The contract

`.covcheck.json` holds a floor per package plus one for the module. Floors, not
targets: a build fails when a package drops below its number.

Per package rather than one total, for two reasons. A single number lets a
well-tested package pay for a neglected one. And it says nothing about where to
work, which is the only question that matters when the goal is 100%.

```sh
covcheck report      # the table
covcheck gate        # silent on success, exit 1 on any package below its floor
covcheck ratchet     # raise every floor to what the suite reaches now
covcheck uncovered   # what to test next
covcheck lcov        # feed genhtml and the other OSS viewers
covcheck merge       # union several profiles
```

The ratchet only ever raises a floor. If coverage genuinely has to fall — a
package deleted, a feature cut — the floor is edited by hand and the diff
carries the argument. Automating the fall would undo the point of having one.

Exclusions require a reason:

```json
{ "pattern": "kura/internal/plan/generated.go", "reason": "generated by go:generate" }
```

An exclusion without one is how a coverage target rots: six months later nobody
remembers whether the file was untestable or merely inconvenient, and the safe
move is always to leave it excluded. `covcheck` refuses to load a config with a
bare pattern.

### Why no coverage service

Codecov and Coveralls are free for public repositories and paid for anything
self-hosted, which this is not going to be. Everything here runs locally or in
CI and writes files: an HTML report, an lcov tracefile, a markdown table for a
job summary. The lcov output is the escape hatch — `genhtml`, `gocovsh` and
`go-cover-treemap` all read it or the profile directly, and all three are in the
dev shell.

If a coverage dashboard with history is ever wanted, SonarQube Community Build
is the self-hostable option and consumes the lcov file as-is. Nothing here
needs changing for it.

### Why covcheck is its own module

`tools/covcheck/` has its own `go.mod`. The binary's rule is standard library
only, and a nested module keeps that provable — `go list -deps ./...` in the
root module never reaches it. It also keeps tooling out of the coverage
denominator: a 100% target is meaningless if it counts code that exists only to
measure coverage.

### Pinning the denominator

`-coverpkg=kura/...` spans the module, so a test in one package credits the code
it drives in another. Without it every package flatters itself by measuring only
its own files — the difference here was 81.6% against an honest 67.4%.

One consequence worth knowing: a package linked into no test binary does not
appear in that pod at all. The instrumented CLI binary links everything, so its
pod pins the full denominator whenever e2e coverage is in the merge.

## End-to-end

### What a VM buys

Everything in `internal/` is already tested in-process, and those tests are
faster and more precise than a VM will ever be. The scenarios exist for the
things a temp directory cannot produce:

| | |
|---|---|
| **Real capacity** | A cartridge is a block device with a filesystem on it. When a plan over-promises, the refusal comes from the kernel, not from kura's own arithmetic. |
| **Real swaps** | Every `kura write` starts, writes one volume, and exits before the next cartridge is mounted. That is the contract the whole tool exists for, and it is only meaningful across processes. |
| **Real ctime** | DESIGN §6 turns on ctime being nanoseconds while mtime is seconds. That is ext4's behaviour, not a mock's. |
| **Real crashes** | `machine.crash()` is a power cut. `Put` deliberately does not fsync, so what survives is the medium's business — and the archive still has to converge. |
| **os.Exit paths** | Every argument error, every refusal, every `fatal()` ends the process. No in-process test survives one. They are most of `cmd/kura`. |

### Adding a scenario

Drop a file in `nix/e2e/scenarios/`. Nothing else is edited — not the flake,
not CI, not a registry. The directory is read at evaluation time and each file
becomes `checks.<system>.e2e-<name>`.

```nix
# nix/e2e/scenarios/my-thing.nix
{ lib, pkgs }:

{
  description = "one line, printed at the top of the log";

  cartridges = [ 192 192 ];   # MB per slot; each gets a qemu serial
  memorySize = 2048;          # optional
  diskSize = 6144;            # optional
  extraModules = [ ];         # optional NixOS config

  script = ''
    machine.start()
    machine.wait_for_unit("multi-user.target")

    with subtest("it does the thing"):
        make_source(machine, spec="tiny=100,small=40", seed=1)
        kura(machine, "plan", "-root", STORAGE, "-catalog", CATALOG, "-out", PLAN,
             "-capacity", "48MB")
        volumes = plan_volumes(machine)
        blank(machine, 1)
        write_volume(machine, 1, volumes[0])
        assert_contains(verify_volume(machine, 1, volumes[0]), "Clean.")
  '';
}
```

Coverage collection is appended automatically. A scenario cannot forget it.

### The helpers

`nix/e2e/prelude.py` is prepended to every scenario, so a scenario file is the
story and not the plumbing.

| | |
|---|---|
| `kura(machine, *args, check=True)` | run it; `check=False` asserts it *fails* |
| `kura_status(machine, *args)` | `(status, output)`, no assertion either way |
| `make_source(machine, spec=, seed=)` | a deterministic tree shaped like the real archive |
| `blank / load / unload` | format a cartridge, insert it under a volume ID, eject |
| `write_volume / verify_volume / restore_volume` | load, run one command, eject |
| `plan_volumes(machine)` | the volume IDs a plan lays out |
| `delta_counts(report)` | the DELTA table as numbers |
| `assert_trees_identical(machine, a, b)` | `diff -r`, so a failure names the file |
| `restored_path(into)` | where a restore actually lands |

`nix/e2e/mktree.py` runs inside the VM: `gen`, `mutate`, `manifest`,
`corrupt`, `corrupt-member`, `fill`.

Two properties are deliberate. The trees are **deterministic** — same seed,
byte-identical files — so a failure reproduces. And the bucket sizes straddle
the 1 MB tar threshold, because that threshold is the decision the whole
on-media layout rests on; a tree of uniformly sized files would exercise one
side of it and report success.

### What the driver does to your script

Three things surprise people, all of them worth knowing before the first
scenario:

- **Every command runs under `set -euo pipefail`.** `find a b | wc -l` fails
  outright when `b` does not exist yet — which is the normal state while a
  write is in progress — rather than counting what it found. Guard with
  `|| true`, or use `count_files()`.
- **The script is type-checked.** `re.search(...).group(1)` is rejected,
  because `search` can return `None`. Put the parse in a prelude helper that
  handles it.
- **The script is linted.** An import in the prelude that no scenario uses
  fails every scenario, since the prelude and the scenario are checked as one
  file.

Timing is the other trap. The driver polls on the order of a second, so
anything that has to happen *during* a write cannot be driven from the driver
side — a hundred-megabyte write finishes in about one poll. `killwhen` runs the
watch loop inside the guest for exactly this reason.

### Cartridges

Slots are addressed by qemu serial (`/dev/disk/by-id/virtio-kura-slot-N`),
never by kernel device order. `/dev/vdb` happening to be slot 1 is true today
and is not a promise, and a scenario that silently formats the wrong disk is an
expensive afternoon.

`load(machine, slot, volume_id)` takes both because they are the same thing only
when the operator loads the right cartridge, and the interesting scenarios are
the ones where they are not.

### Scaling

Each scenario is an independent derivation. Nix runs them in parallel up to
`max-jobs`, caches the ones whose inputs did not change, and attributes a
failure to exactly one scenario. Adding the fiftieth scenario costs one file and
one VM boot, not an edit to a shared driver.

For CI, `nix flake check` runs everything; sharding is a matter of splitting the
scenario list across runners and building the named checks. `.github/workflows/`
has it.

### Debugging one

```sh
make e2e-1 S=bitrot          # run it with logs
make e2e-shell S=bitrot      # boot the VM and drive it by hand
```

The interactive driver gives a Python REPL with `machine` and every prelude
helper in scope.

## The scenarios

| | |
|---|---|
| `smoke` | the harness itself: cartridges appear, kura runs, counters come back. Also every argument-error path, which all end in `os.Exit`. |
| `full-cycle` | plan, write across cartridges with real ejects, verify, restore, compare byte for byte. Checks the on-media layout against DESIGN. |
| `cartridge-swap` | the wrong cartridge, refused four ways: by header, by drive identity, by a volume the plan lacks, and as a foreign archive. |
| `bitrot` | a byte flipped at a computed offset inside one tar member. Verify must blame that file and no other, mark it lost, and the next plan must re-source it. |
| `incremental` | a second generation. Content changed behind an unchanged size *and* mtime, so only ctime differs; deletions and additions; restore of either generation. |
| `capacity` | a plan that over-promises the medium. The refusal comes from the kernel, and nothing is recorded as written. |
| `interrupted-write` | SIGKILL mid-write, then a power cut mid-write. Both must resume to a volume that verifies and restores. |

`cmd/kura` is the whole argument: it is argument handling, refusals and
operator output, nearly all of it behind an `os.Exit` that no in-process test
survives. Seven VM scenarios took it from a quarter covered to seven eighths.

The floors in `.covcheck.json` are the right-hand column, rounded down. 332
statements in 274 blocks remain — `covcheck uncovered` lists them, and after
the easy ones they are mostly I/O error paths that need injected failures
rather than more scenarios.

Note the honest denominator. Measured per package in isolation the unit suite
reads several points higher; `-coverpkg=kura/...` is what turns that into
67.41%, and the lower number is the true one.

To raise the floors after adding tests:

```sh
make cover-gate                  # merges unit + e2e into coverage/all.profile
make cover-ratchet               # raises every floor to what that reached
```

### Three defects found so far, all fixed

Each is now a regression test in the scenario that found it.

**Deletions were never recorded** (`incremental`). `catalog.Record.DeletedGen`
existed, `Catalog.At` honoured it, `scan.Diff` collected deleted records, and
the plan report said "tombstoned, data retained" — but nothing outside test
fixtures ever assigned it. `kura at-gen` listed files deleted generations ago,
and a restore of the newest generation recreated them.

This one is instructive about why the VM suite exists. The *reading* half of
tombstoning is thoroughly unit-tested against hand-written records, so coverage
over `catalog` and `scan` looked fine. Nothing noticed that no producer existed,
because no unit test ever ran a real cycle end to end. The plan file now carries
the deleted paths and `write` applies them idempotently, so a cycle that only
removed files still records the generation.

**An interrupted first write orphaned the cartridge** (`interrupted-write`). The
archive ID was minted in memory, stamped onto the medium before the first object,
and persisted locally only once the whole volume succeeded. A kill, a power cut
or a full medium in between lost it; the next run minted a different one and
refused the cartridge as foreign, permanently — a window of hours on real
hardware. Identity now lives in its own write-once object, is persisted before
any object is written, and a catalog that has lost it adopts the medium's.

**A second generation on one cartridge left a stale index** (`full-cycle`). The
on-volume catalog was named by copy number, so a later cycle found
`kura.catalog.000/001` taken and skipped them — the cartridge kept an index
describing only the first cycle. Silent, because nothing reads the on-volume
catalog back until the local one is gone, which is the one moment it has to be
right. Per-cycle metadata now lives under `generations/gNNNN/`, which is also
what LTFS does with its own index.
